The conversation focused on building a small CustomTkinter floating overlay/toolbar, fixing button sizing and dragging behavior, making buttons rounded, launching external scripts with `subprocess.Popen()`, and running cleanup code when the window closes.

Key points and code issues identified in the original `Overlay` code:
- The window size `50x150` is too narrow for normal `CTkButton` text like `"Close"` and `"Start"`, making the buttons appear too large or awkward.
- `CTkButton` has a default size/style that is larger than raw tkinter widgets, so ultra-small layouts can feel cramped.
- `self.grid_columnconfigure(0, weight=0)` prevents the column from expanding; `weight=1` is better when using `sticky="nsew"`.
- There was a naming conflict:
  - `def move(self, event):`
  - `self.move = False`
  This overwrites the method with a boolean and breaks functionality.
- The original drag logic used a blocking `while self.move:` loop, which is not appropriate for GUI apps because it freezes or blocks the event loop.

Recommended fixes for the overlay/buttons:
- Increase window width, e.g. `self.geometry("100x150")` or similar.
- Set `self.grid_columnconfigure(0, weight=1)`.
- Optionally give buttons explicit dimensions like `width=80, height=40`.
- Rename the movement boolean to something like `self.is_moving`.
- Use event bindings for dragging instead of a `while` loop.

A cleaned-up draggable floating toolbar version was proposed with these characteristics:
- Uses `self.overrideredirect(True)` to remove the title bar.
- Uses `self.attributes("-topmost", True)` to keep it on top.
- Example geometry: `"90x120+300+300"`.
- Stores drag offsets as instance variables.
- Creates three vertically stacked buttons: Close, Move, Start.
- Binds:
  - `"<Button-1>"` to begin dragging
  - `"<B1-Motion>"` to move the window
- `Close` button calls `self.destroy()`.
- `Start` button can call a custom function like `self.start_action()`.

Compact/tiny toolbar suggestions:
- Smaller geometries such as `"70x105+300+300"` or `"60x90+300+300"` were suggested.
- Smaller labels like `"X"`, `"M"`, `"Go"` help when making very small buttons.
- If the goal is an ultra-compact utility overlay, normal tkinter may be easier than CustomTkinter because CustomTkinter has a built-in modern, padded visual style and a minimum “visual feel”.

Dragging details and correct event attribute names:
- The user asked whether the correct mouse coordinates were `event.rootx` / `event.rooty`; the correction was:
  - correct: `event.x_root`, `event.y_root`
  - incorrect: `event.rootx`, `event.rooty`
  - also incorrect: `event.root_x`, `event.root_y`
- Difference between coordinate types:
  - `event.x`, `event.y` = mouse position relative to the widget
  - `event.x_root`, `event.y_root` = mouse position relative to the screen
- For dragging windows smoothly, an offset should be computed so the window does not snap its top-left corner directly to the mouse.
- Suggested drag logic:
  - on mouse-down: store offset using current window position vs root coordinates
  - on drag: compute new window position using those offsets and call `geometry(...)`

Rounded / circular button discussion:
- `CTkButton` supports rounded rectangles, not true circles.
- To make buttons rounded, use the `corner_radius` parameter.
- For pill-shaped buttons:
  - Example: `width=100, height=50, corner_radius=25`
- For circle-like buttons:
  - Make width and height equal
  - Set `corner_radius` to half the height
  - Example: `width=50, height=50, corner_radius=25`
- Rule of thumb:
  - `corner_radius = height / 2`
- Setting the radius larger than half the height usually does not make it look any rounder.
- For truly circular buttons, alternatives suggested were:
  - drawing on a `Canvas`
  - using images/icons
  - faking it with a custom-drawn widget
- Example idea for rounded buttons:
  - `ctk.CTkButton(..., corner_radius=20)`
- Example for circle-like button:
  - `ctk.CTkButton(..., text="X", width=40, height=40, corner_radius=20)`

`subprocess.Popen()` discussion for launching another process:
- The user asked how to make a subprocess separate and suppress the terminal.
- On Windows, suggested flags included:
  - `subprocess.CREATE_NEW_PROCESS_GROUP`
  - `subprocess.DETACHED_PROCESS`
  - `subprocess.CREATE_NO_WINDOW`
- Example for launching another Python script silently:
  - use `Popen([...], creationflags=..., stdin=DEVNULL, stdout=DEVNULL, stderr=DEVNULL)`
- `Popen()` does not wait; `run()` does wait.
- If launching a GUI Python script, using `.pyw` can avoid opening a console window at all.
- `DETACHED_PROCESS` is more relevant for console programs or Python console scripts than GUI apps.
- If the goal is “run it in the background and don’t freeze the parent terminal,” `Popen()` already accomplishes that.

Launching a `.vbs` file:
- Launching a VBS file via `subprocess.Popen()` on Windows is fine.
- Recommended to explicitly call:
  - `wscript.exe` for no console window
  - `cscript.exe` only if console output is desired
- Example pattern:
  - `subprocess.Popen(["wscript.exe", r"C:\path\to\script.vbs"], ...)`
- Suggested to pass VBS path as a separate list item, even if it contains spaces.
- Using `shell=True` with the VBS file can work, but explicitly calling `wscript.exe` is cleaner and more predictable.
- In most cases, `DETACHED_PROCESS` is not necessary for launching a `.vbs` through `wscript.exe`.
- Practical recommendation:
  - first try just `wscript.exe + Popen`
  - add `CREATE_NO_WINDOW` only if needed
- Bottom line: for launching a VBS from a Tkinter/CustomTkinter app, `DETACHED_PROCESS` is usually not needed.

Running code when the window closes:
- The user asked whether code can execute when the window is destroyed via the title bar X.
- Yes: use `self.protocol("WM_DELETE_WINDOW", self.on_close)`.
- In `on_close()`, do cleanup/custom behavior first, then call `self.destroy()`.
- Example use cases for `on_close()`:
  - print a message
  - launch a subprocess/VBS
  - save settings
  - stop threads
- If there is also a custom Close button, it should call the same `on_close()` function instead of calling `destroy()` directly.
- Important caveat:
  - if `self.overrideredirect(True)` is used, the normal title bar is removed, so there is no X button to click.
  - In that case, `WM_DELETE_WINDOW` won’t apply to a title-bar X because there is no title bar.
  - For borderless windows, a custom Close button should call `on_close()`.
- It is safer to do custom work before calling `destroy()`, not after, especially if the logic depends on the window object still existing.
